1. 从一个样本建立四个知识模块的联系

假设要做一个温度采集控制器：定时采样，温度过高时开启风扇，通过串口上传状态。先沿着一个样本走一遍：

定时器触发 ADC → ADC 产生数值 → DMA 写入 RAM
                                      ↓ 完成中断
                             把样本交给处理者
                                      ↓
                     换算温度 → 检查有效性 → 状态机
                                      ↓
                            更新风扇 / 上传状态

图中每一条箭头都值得问：谁来执行、数据存在哪里、谁能修改、最迟什么时候完成、失败以后怎么办？ 这五个问题就是后面所有考点的共同骨架。

1.1 先把常见术语翻译成具体对象

术语 在本例中指什么
CPU / 内核 执行指令，响应异常；ADC、DMA 不属于 CPU 指令本身

2. 单片机高频题：程序如何与硬件配合

2.0 先建立模型：CPU 执行指令，外设按自己的状态机工作

从一条 C 语句追到引脚

GPIOx->ODR |= mask 在典型内存映射外设中表达的是：读取输出寄存器、把掩码对应的位设为 1、再写回。编译器把它转换成目标机器的指令，CPU 通过总线访问外设，外设根据引脚模式和寄存器状态驱动引脚。

因此，“代码执行了”不等于“引脚一定变高”：还需要外设时钟开启、引脚复用正确、电气模式正确，也要确认你写的寄存器确实控制这个引脚。这条链路帮助你把软件排错和硬件排错连起来。

下面只操作普通 RAM 变量，是位运算教学片段；真实寄存器必须先读手册确认访问宽度和读写语义。

#include <stdint.h>
uint32_t value = UINT32_C(0xA0);   /* 二进制 ...1010 0000 */
value |= UINT32_C(1) << 2;         /* 置 bit 2，得到 0xA4 */
value &= ~(UINT32_C(1) << 5);      /* 清 bit 5，得到 0x84 */
uint32_t field = (value >> 2) & UINT32_C(3); /* 读 bit 3:2，得到 1 */

反例：若状态寄存器中的标志位“写 1 清零”，STATUS |= flag 会先读取全部已置位标志，再将它们一并写回，可能顺带清掉别的事件。此时应按手册指定方式写入需要清除的掩码；若存在特殊保留位要求，也必须一并满足。

GPIO 的“1”为什么有时不是主动输出高电平

推挽输出通常能主动拉高和拉低；开漏输出通常只能主动拉低，输出“1”表示释放线路，由上拉电阻使它升高。因此 I²C 上拉太弱、总线电容太大时，软件寄存器已经写“1”，实际电压仍可能上升太慢。悬空输入、错误复用和上下拉配置都能造成“程序正确但读值不对”。

中断为什么能在函数执行一半时插进来

以常见 Cortex-M3/M4 基本异常栈帧为例，异常入口硬件保存 R0–R3、R12、LR、PC、xPSR，然后执行处理程序；异常返回按保存的现场恢复。额外的保存、栈对齐及浮点扩展取决于具体内核、编译器和异常情况。普通函数调用不等于一次异常入口。

中断的作用是让 CPU 及时处理事件；DMA 的作用是让数据搬运可以由独立硬件进行。二者往往协作：DMA 搬完一块数据后才中断 CPU。它们都不会自动替应用保证缓冲区生命周期。

先列时间预算，再讨论“够不够快”

假设定时器输入为 72 MHz，向上计数、无重复计数等特殊配置，取 PSC=71，得到 1 MHz 计数时钟；再取 ARR=999，每 1000 次计数产生一次更新，即 1 kHz。一次采样触发间隔是 1 ms，不能把 CPU 的主频直接当作采样率。

实时路径的延迟要把“事件等待响应、中断处理、任务等 CPU、等锁、业务处理”分别算进去。这些分项必须避免重复计数，并覆盖可能发生的干扰。 平均处理 100 μs，并不能证明每次都能在 1 ms 内完成。

下面的 13 道题分别补齐启动、内存、事件、电气接口、故障恢复这条主线。

2.1 上电后为什么不是立刻执行 main？

答案：以 Cortex-M 为例，复位后内核从向量表取得初始主栈指针和复位处理入口，进入启动代码。启动代码通常复制已初始化数据到 RAM、清零 .bss、完成运行库和系统初始化，然后调用 main。

解析：C 程序默认全局已初始化变量可读、零初始化变量为零，这些条件需要在 main 前建立。向量表映射地址和启动顺序由芯片、链接脚本及启动文件共同决定；不要把某款 STM32 的 Flash 地址当作所有 Cortex-M 的固定地址。想继续深入可读本站的《单片机复位到main函数的过程》。参考 Arm Cortex-M 处理器资料。

2.2 Flash、RAM、栈和堆分别装什么？

答案：程序指令和常量通常放在 Flash；运行时可写数据在 RAM。栈通常保存函数调用现场、局部自动对象及任务上下文；堆用于动态申请。它们是用途和链接布局，不是 C 语言强制规定的某几个物理地址。

解析：.data 初值常存于 Flash，启动时复制到 RAM；.bss 在 RAM 中清零；const 对象放在哪里取决于工具链和链接脚本。FreeRTOS 的每个任务通常有自己的栈，而中断栈如何使用取决于移植端。易错点：“局部变量一定在栈上”“const 一定在 Flash”都不是无条件成立。

2.3 中断、轮询和 DMA 怎么选？

答案：低频、简单状态检查可轮询；不规则事件可用中断及时响应；连续或成块搬运数据通常考虑 DMA，并用中断通知传输完成。

解析：中断减少等待，但每次进入都有现场处理开销；DMA 降低 CPU 搬运负担，却要处理缓冲区所有权、完成时机和缓存一致性。典型 UART 接收方案是“DMA 写环形缓冲区 → 空闲/半满/满事件 → 任务解析”。易错点：DMA 不等于零 CPU 开销，也不自动保证数据已经对 CPU 可见；带数据缓存的芯片需按手册维护缓存。

2.4 为什么中断服务函数要短？

答案：中断会打断当前执行流；处理过久会提高其他中断的响应延迟，并可能破坏实时性。ISR 一般只确认事件、保存必要数据、清除中断源和唤醒后续处理者。

解析：例如串口中断先读状态与数据、放入缓冲区，再通知解析任务。不要在 ISR 中等待互斥锁、做长时间打印或调用可能阻塞的函数。易错点：“短”不是固定微秒数，应按最坏执行时间和系统截止期评估。Arm 的 NVIC 支持嵌套、自动保存现场等机制，见 Arm 中断延迟说明。

2.5 中断优先级数字越大，优先级越高吗？

答案：在常见 Cortex-M NVIC 的逻辑优先级中，数字越小，紧急程度越高；实际可配置位数、分组和库函数的参数表示方式要看芯片及 CMSIS/HAL。

解析：任务优先级和硬件中断优先级是两套体系，不能直接比较。若使用 FreeRTOS 的 ...FromISR() API，中断还必须处于该移植端允许调用内核 API 的优先级范围。优先级 0 往往过高，直接用来调用内核 API 很危险。参考 Arm 优先级解释和 FreeRTOS 中断优先级配置。

2.6 volatile 为什么常用于外设寄存器和中断共享标志？

答案：被声明为 volatile 的对象每次访问都要按该实现的规则保留可观察访问，适合描述可能被硬件或异步执行路径改变的值。

解析：轮询状态寄存器时，编译器不能把读取简单缓存成一次；ISR 修改的标志也需要让主程序重新读取。但 volatile 不保证原子性、互斥、跨核内存顺序或整体线程安全。共享计数器的 count++ 是读、加、写，仍可能丢更新。C11 对 volatile 的精确定义见 WG14 N1570 §6.7.3。

2.7 什么是原子操作？关中断就一定安全吗？

答案：原子操作对其他参与者表现为不可拆分。关中断可以在同一内核、相关共享者只在当前线程和可屏蔽 ISR等条件下保护短临界区；它不是所有平台上的通用锁。

解析：DMA、另一颗核、不可屏蔽中断不会因为本核普通关中断就停止。对寄存器读改写也要看硬件是否提供置位/清零专用寄存器。临界区应尽量短，并使用芯片或 RTOS 提供的匹配进入/退出接口。

2.8 定时器如何算更新周期？为什么实际频率不对？

答案：对典型向上计数定时器，在没有特殊计数模式和额外分频时，更新事件频率可写为 f_update = f_timer / ((PSC + 1) × (ARR + 1))。

解析：先确认真正输入定时器的时钟 f_timer，再检查预分频寄存器 PSC、自动重装寄存器 ARR 的“加一”关系。某些芯片的总线分频会改变定时器时钟；中心对齐 PWM、重复计数器也会改变事件频率。例子：1 MHz 定时器时钟、PSC=99、ARR=999，更新频率为 10 Hz。

2.9 UART、SPI、I²C 最核心的区别是什么？

答案：UART 通常是异步、点对点收发；SPI 通常由时钟同步，主从双方可同时移位；I²C 是带地址和应答的共享总线，常见物理实现为开漏配上拉。

解析：“全双工/半双工”只是其中一个维度，还要考虑引脚数、寻址、速率、距离与错误恢复。UART 要确认波特率、帧格式和错误标志；SPI 要确认模式 CPOL/CPHA、片选与字节序；I²C 要确认上拉、地址、ACK/NACK、时钟拉伸及总线卡死恢复。具体速率不是由协议名称单独决定的。

2.10 ADC 采样值不稳，先查什么？

答案：先区分真实输入噪声、参考电压变化、采样时间不足、源阻抗过高、时序问题和数字处理造成的抖动。

解析：ADC 输入采样电容需要充电时间；高阻传感器与短采样窗口容易出现前一通道残留。检查参考电压、接地、滤波、电源和通道切换后的首样；再看过采样或平均是否适合信号带宽。易错点：均值滤波只能压低某些随机噪声，不能修复错误接线或系统性偏差。

2.11 看门狗如何正确使用？

答案：看门狗要求软件在规定时间内喂狗，超时触发复位或其他动作；喂狗应代表关键功能确实在正常推进。

解析：若在永远会运行的定时中断里无条件喂狗，业务任务死锁时仍可能持续喂狗。更稳妥的设计是监控各关键任务的心跳、执行周期和故障标志，由健康管理模块在条件全部满足时喂狗。窗口看门狗还要求不能喂得太早。复位后读取复位原因并记录故障上下文。

2.12 HardFault 出现后先怎么定位？

答案：保留故障现场，读堆栈中的 PC/LR、故障状态寄存器与当前栈指针，对照 ELF/映射文件定位指令，再追查越界、空指针、栈溢出、未对齐访问等原因。

解析：不能只看最后进入的 HardFault_Handler，那只是异常入口。异常可能由更早的数据破坏引起；若重启后才读故障信息，现场往往已经丢失。故障寄存器的存在和含义取决于 Cortex-M 型号。面试加分点：说出“先判断 MSP/PSP 和异常返回值，再找故障指令与调用链”。

2.13 Bootloader 和应用程序如何分工？

答案：Bootloader 负责启动决策、固件校验与升级回退；应用程序负责业务功能。跳转前要确认目标镜像有效、设置向量表与栈，整理中断和外设状态。

解析：不能只把 PC 指向应用的 main：应用需要自己的复位入口、向量表和初始化流程。可靠升级通常先写非当前运行区，验证完整性和版本，再切换启动标记；断电恢复策略需要提前设计。签名认证和完整性校验解决的问题不同。

2.14 模块自测：解释硬件现象

先回答：① 72 MHz 输入、PSC=71、ARR=999，一秒更新几次？② DMA 正在写 RAM，关本核中断能否让它停止？③ 给 GPIO 写“1”后引脚仍低，至少查哪三项？

答案与推理：① 1000 次，因为两级除数分别为 72 和 1000。② 不能，DMA 是独立的总线访问者，应按外设流程停机或交接缓冲区。③ 查时钟、引脚复用/模式、实际寄存器与引脚对应关系；开漏还要查上拉和是否有其他器件拉低。能把“代码—总线—外设—引脚”串起来，比单说“检查硬件”更有用。

3. C 语言高频题：表达、内存和未定义行为

以下按 C11 回答。遇到“输出是什么”题，先判断是否有未定义行为、实现定义行为或未指定顺序，再考虑具体数值。语言规则可核对 WG14 的 C11 委员会草案 N1570；编译器扩展与目标 ABI 还要看工具链文档。

3.0 先建立模型：类型、对象、地址和生命周期

读一段 C 代码时先问四件事

  1. 这是哪个对象，实际占多少存储？
  2. 表达式的类型是什么，会发生哪种隐式转换？
  3. 对象从何时存在到何时，访问时还有效吗？
  4. 同一时刻还有谁会修改它？

下面是函数体内的教学片段，int 的大小暂不假设为 4。

int a[3] = {10, 20, 30};
int *p = a;
int (*whole)[3] = &a;

a 是数组对象：     [10] [20] [30]
p 是指针对象：      └── 指向 a[0]
whole 是指针对象：  └── 指向整个 a（类型为“指向含 3 个 int 的数组”）

p + 1     → 指向 a[1]
whole + 1 → 越过整个 a，成为该数组对象的尾后指针，不可解引用

sizeof a == 3 * sizeof(int)；sizeof p 由目标平台的指针类型决定。二者即使碰巧数值相等，也不表示数组与指针相同。把 a 传给声明为 void f(int a[3]) 的函数时，形参调整为指针，长度不会自动随指针一起传递。

把生命周期和存储位置分开想

对象 生命周期 常见风险
块内普通非 VLA 自动对象 进入关联块到离开该块 返回其地址、交给异步使用者
静态存储期对象 整个程序执行期间 多调用者共享、并发覆盖
动态申请的对象 从成功分配到释放 泄漏、重复释放、释放后使用

普通非 VLA 自动对象的生命周期从进入关联块开始，名字的作用域则从声明处开始，二者不是同一个概念；变长数组另有规则，见 C11 §6.2.4。编译器可能把变量放进寄存器甚至消除实体存储，但它仍要遵守有定义程序的可观察语义。

通信字节不能随便强转成指针

假设协议给出两个小端字节，buf[0] 是低位。*(uint16_t *)buf 可能遇到未对齐、有效类型以及本机字节序问题。逐字节组装可以把协议写清楚。以下函数要求 uint8_t、uint16_t 可用，输入至少两个有效字节，输出指针指向可写对象。

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

bool read_u16_le(const uint8_t *buf, size_t len, uint16_t *out)
{
    if (buf == NULL || out == NULL || len < 2) {
        return false;              /* 失败时不修改 *out */
    }
    *out = (uint16_t)((uint32_t)buf[0] | ((uint32_t)buf[1] << 8));
    return true;
}

输入 {0x34, 0x12}，结果是 0x1234，即十进制 4660。指针参数传的是地址值，长度参数传的是可读范围，二者缺一不可。NULL 检查也不能证明一个非空指针真的指向有效存储，这仍是调用方的责任。

为什么 volatile count++ 还是可能丢更新

设任务与 ISR 都修改同一个计数器，初值为 5。在目标编译器将自增实现为读、加、写，且允许中断介入的情形下：

时刻 任务 ISR 内存中的值
1 读到 5，尚未写回 — 5
2 被中断 读 5、加 1、写 6 6
3 用先前的 5 计算并写 6 已返回 6

逻辑上加了两次，实际只增加一次。修复应选择适合共享者的临界区、消息传递或经端口验证可用的原子操作；不能靠再加一个 volatile。C11 _Atomic 也并非必然无锁，ISR 能否使用还需检查实现。

下面的题用这套模型分析声明、指针、布局和表达式，不靠记住某次编译的结果。

3.1 static 在函数内和文件作用域分别做什么？

答案：函数内 static 对象具有静态存储期，但名字只在该块可见；文件作用域 static 变量或函数具有内部链接，只在当前翻译单元中用这个名字访问。

解析：局部静态变量不会每次调用都重新创建，若没有显式初始化则为零初始化。文件作用域 static 常用于隐藏模块内部细节。static 不等于常量，也不自动保证线程安全。

3.2 声明、定义和 extern 有什么区别？

答案：声明告诉编译器名字与类型；定义提供对象存储或函数实体。extern int count; 通常只是引用别处的定义，int count = 0; 是定义。

解析：头文件里通常放声明，某一个 .c 文件里放唯一外部定义。把非 static 的变量定义直接放头文件，多个源文件包含后容易出现重复定义。头文件中的函数原型不创建函数体。

3.3 const、volatile 和 const volatile 怎么读？

答案：const 限制通过该限定类型的左值修改；volatile 表示访问不能按普通对象那样省略或随意合并；const volatile 常表示“软件只读，但硬件可能改变”的寄存器。

解析：const uint8_t *p 是“指向只读数据的指针”，uint8_t * const p 是“指针本身不能改指向”。若对象本身定义为 const，强制转型后修改会导致未定义行为。C 中的 const 也不保证对象一定放在只读物理存储器。

3.4 数组和指针完全一样吗？

答案：不一样。数组是包含连续元素的对象；指针是保存地址值的对象。多数表达式中数组名会转换为指向首元素的指针，但 sizeof array 和 &array 等场景不会做这种转换。

解析：局部 int a[10] 的 sizeof a 是整个数组的字节数；函数参数写成 int a[] 实际调整为指针参数，在函数里 sizeof a 是指针大小。a + 1 跨一个元素，&a + 1 跨整个数组。

3.5 sizeof、strlen 和缓冲区容量有什么区别？

答案：sizeof 给对象或类型的字节大小，strlen 扫描到首个 \0 前的字符数；缓冲区容量是可存储的总字节数，可能与当前字符串长度不同。

解析：char s[8] = "abc"; 中 sizeof s 为 8，strlen(s) 为 3；末尾的 \0 仍占 1 字节。sizeof(char) 按定义为 1，但一个字节的位数由 CHAR_BIT 给出，并非所有 C 实现都强制为 8。

3.6 指针参数为什么有时需要二级指针？

答案：C 语言参数按值传递。传入 T *p 可修改 p 指向的对象，却不能通过只修改局部 p 改变调用者的指针变量；要改调用者指针，传 T **，或返回新指针。

解析：void reset(Node *p) { p = NULL; } 不会让调用者的指针变空；void reset(Node **p) { *p = NULL; } 才会。使用二级指针前仍需检查传入地址有效，且不能把局部对象地址返回给调用者。

3.7 为什么返回局部变量地址是错的？

答案：普通局部自动对象在离开作用域后生命周期结束，指向它的指针变为悬空；解引用会产生未定义行为。

解析：改为由调用者提供缓冲区、返回结构体值、使用明确所有权的动态分配，或在确实只需单实例且考虑并发时使用静态对象。静态对象虽不会悬空，但多次调用共享同一存储，可能产生覆盖和并发问题。

3.8 结构体大小为什么常大于成员大小之和？

答案：编译器可能在成员间和末尾插入填充，以满足对齐要求及数组元素布局。

解析：struct { char c; int x; char d; } 的大小不能脱离 ABI、成员对齐和打包选项直接断言。可用 sizeof、offsetof 和 _Alignof 在目标编译器上验证。不要把普通结构体内存原样当跨平台通信报文；布局、字节序、填充字节都可能不同。本站《结构体细节探究》有更完整的推导。

3.9 位域适合直接映射外设寄存器或协议帧吗？

答案：一般不建议把位域布局作为跨编译器、跨平台协议或寄存器定义的唯一依据，因为位域分配顺序、对齐等存在实现相关部分。

解析：用明确宽度的整数掩码和移位可把位位置写清楚，例如 (reg & MASK) >> SHIFT。但外设寄存器还要考虑“写 1 清零”、只读位及读改写副作用，不能机械地 reg |= bit。协议解析更适合逐字节组装。

3.10 有符号与无符号混算为什么危险？

答案：通常的算术转换可能把负的有符号值转换成较大的无符号值，导致比较和减法结果出乎直觉。

解析：例如 int i = -1; unsigned int u = 1;，表达式 i < u 为假：int 与 unsigned int 的转换等级相同，i 会转换为 UINT_MAX 后比较。判断数组长度时也要避免 len - 1 在 len == 0 且为无符号时下溢。先检查范围，再做运算；位操作优先使用合适的无符号类型。

3.11 左移和右移有哪些边界？

答案：移位次数必须非负且小于左操作数提升后的位宽；对无符号类型的移位规则更适合表达位掩码。负有符号值左移，以及有符号左移结果不可表示等情况会导致未定义行为。

解析：优先写 UINT32_C(1) << bit 并检查 bit < 32，不要把 1 << 31 默认当成可移植的 32 位最高位掩码。有符号负数右移的结果属于实现定义，应避免依赖它实现协议运算。

3.12 宏和 static inline 有何区别？

答案：宏是预处理文本替换；static inline 是具有类型检查、参数求值规则和函数作用域的函数定义，是否真正内联由编译器决定。

解析：#define SQR(x) ((x) * (x)) 调用 SQR(i++) 会多次求值，有副作用风险。简单常量可用宏或枚举；短函数优先考虑 static inline。多语句宏若必须使用，常包在 do { ... } while (0) 中，并给参数和整体表达式加括号。

3.13 大端、小端和字节序如何判断？

答案：字节序描述多字节对象在内存中的字节排列；小端把最低有效字节放在较低地址，大端相反。

解析：它不改变数值本身，也不等于串口线上每个字节的位传输顺序。协议通常规定“网络字节序”或逐字段序列化，不能把 uint32_t 对象直接 memcpy 到线缆上就认为跨平台一致。组帧时显式写每个字节最清楚。

3.14 memcpy、strcpy、strncpy 使用时注意什么？

答案：memcpy 按给定字节数复制，源与目标重叠时应使用 memmove；strcpy 不知道目标容量；strncpy 在源长度达到上限时可能不补 \0。

解析：处理串口数据要保存实际长度，不能假设它以零结尾。拷贝前检查目标容量，拼接字符串时预留结尾零字节。memcpy 适合复制对象表示，但解析协议字段时仍应考虑字节序、对齐和格式版本。

3.15 什么是未定义行为？笔试题怎样判断？

答案：未定义行为是 C 标准对该程序行为不作要求，不能给出一个可移植的“正确输出”。

解析：数组越界、解引用悬空指针、有符号整数溢出，以及 i = i++ + 1 这类对同一标量对象有未排序冲突访问的表达式，都是常见例子。不要根据某次编译运行结果反推语言规则。与之不同，实现定义行为要求实现作出并说明选择；未指定行为允许多种合法选择。可查 WG14 N1570 §3.4 与 §6.5。

3.16 函数指针和回调常见用途是什么？

答案：函数指针可把“行为”作为参数传给模块，用于中断回调、设备操作表、状态转换动作和测试替身。

解析：例如 int (*read)(void *ctx, uint8_t *buf, size_t cap) 表示一个接收上下文、缓冲区和容量的读取操作。回调需要明确调用上下文：从 ISR 调用的回调必须遵守 ISR 限制；从任务调用则可按任务规则运行。函数指针类型、上下文对象生命周期和空指针处理都要检查。

3.17 模块自测：先分类，再计算

题目：① char s[8] = "abc"; 的容量、字符串长度、终止符位置分别是什么？② 函数用局部数组组帧，把地址放入队列后返回，为什么不可靠？③ int i=-1; unsigned int u=1;，i < u 是真是假？④ int i=1; int x=i++ + i++; 应答出什么？

答案与推理：① 8 字节、3、s[3]，其余元素也被零初始化。② 队列若只复制指针，数组生命周期结束后没有可用的那份对象；应复制内容或显式移交长期有效存储。③ 假，int 与 unsigned int 同级，i 转成 UINT_MAX 后比较；这不是只在某个常见 32 位平台上才成立。④ 在本文 C11 语境下是未定义行为，两个自增副作用未排序，不能给出标准规定的数值答案。

从“都写进 main”到明确的依赖方向

温度控制程序至少需要采样、换算、判断、驱动输出和通信。若它们都通过全局变量彼此读写，任何一个修改都可能影响整条链。可以按下面的依赖方向组织：

应用协调层：何时采样、何时上传、如何进入安全状态

领域逻辑：温度有效性、风扇状态机、协议含义
     ↓ 通过接口请求
设备驱动：ADC读取、风扇输出、UART传输
     ↓
板级配置与芯片外设接口

给每个接口写一份短契约

一个“读温度”接口至少要回答：返回摄氏度还是毫摄氏度？失败是否修改输出？最多阻塞多久？能否在 ISR 调用？多个任务同时调用是否安全？数据属于谁？

例如，约定 bool sensor_read_milli_celsius(int32_t *out) 只供任务调用、成功才写输出、内部超时有上限。业务模块可以根据 false 进入故障状态；不会误把“旧温度恰好仍在变量里”当作本次测量成功。

用有滞回的风扇例子理解状态

设定“温度达到 30 ℃开启，降至 28 ℃关闭”。28～30 ℃之间保留当前状态，这是滞回，可减少测量抖动导致的反复启停。

当前状态 输入条件 下一状态
关闭 有效温度 ≥ 30 ℃ 开启
开启 有效温度 ≤ 28 ℃ 关闭
开启或关闭 温度处于两阈值之间 保持
任意状态 数据无效 故障
故障 有效数据且明确确认恢复 从关闭状态重新判定阈值

这里只是教学控制器。故障时输出是开启还是关闭，必须由具体产品的危险分析决定；完整案例会为示例明确选定输出行为。

为什么状态机需要记忆？ 同样输入 29 ℃，之前处于开启状态时保持开启，之前处于关闭状态时保持关闭。只写 fan = temperature > 30 无法表达这种行为。

把“谁拥有状态”也设计进去

可以指定控制任务独占状态机对象，通信任务只发送“修改设定值”等消息。这样无需让多个任务直接修改同一个 state。一个消费者拥有数据，并不代表所有程序都要通过一个大队列运行；按模块和流量建立小而明确的边界即可。

4.1 裸机超级循环和 RTOS 各适合什么项目？

答案：任务数量少、时序简单、资源紧张时，超级循环加中断往往足够；多个独立活动需要优先级、阻塞等待和清晰任务边界时，可考虑 RTOS。

解析：超级循环不等于“所有函数一直无条件跑”，可用事件标志、状态机和时间片组织。RTOS 也不自动使系统实时；任务优先级、最坏执行时间和共享资源仍需设计。选择依据是可验证的时序与复杂度，而非“项目越高级越要 RTOS”。

4.2 HAL、BSP、驱动、服务和应用层怎么分？

答案：HAL 封装芯片外设寄存器，BSP 绑定板级引脚和器件连接，设备驱动管理具体器件行为，服务层提供可复用能力，应用层处理产品规则。

解析：例如“读取温度”：HAL 提供 I²C 发送接收；BSP 知道传感器接在哪条总线和哪个电源脚；传感器驱动按芯片手册读取寄存器并换算；温度服务处理滤波与有效性；应用决定何时报警。命名可不同，但依赖方向和职责要清楚。上层不应到处直接改外设寄存器。

4.3 为什么不要把所有逻辑都塞进中断或一个任务？

答案：这样会耦合硬件时序、协议解析和业务决策，使最坏执行时间难估、模块难测、故障难定位。

解析：中断负责取得事件与最小数据；任务或主循环处理缓冲区、协议和业务。过度拆任务也会增加栈占用和同步成本。划分任务时先问：是否有不同优先级、不同等待事件或独立截止期；若没有，一个任务内的状态机可能更合适。

4.4 状态机解决什么问题？

答案：状态机把“系统现在处于什么阶段、收到事件后去哪里、进入或离开时做什么”显式表达出来，适合通信协议、升级流程、设备控制。

解析：例如电机可有 STOPPED → STARTING → RUNNING → FAULT。每个转换需写清条件和动作；故障状态要定义恢复路径。状态机不应靠多个互相矛盾的布尔标志隐式拼出来。面试追问：若突然收到停机命令，所有状态是否都有确定处理？

4.5 驱动接口为什么要区分初始化、启动和读写？

答案：初始化建立资源和默认配置；启动允许设备实际工作；读写执行运行时操作。分开有利于处理依赖顺序、失败回滚和重复启动。

解析：一个好的驱动接口会明确参数单位、超时、返回码、调用上下文和线程安全约束。例如 sensor_read_milli_celsius() 比 sensor_get() 更清楚，调用者知道返回单位。若函数可能阻塞，应在接口注释中写明，避免 ISR 误用。

4.6 如何设计模块间数据所有权？

答案：每一块缓冲区都要约定谁写、谁读、何时交接、何时可以复用。传递结构体值适合小数据；传递指针适合大数据，但必须管理生命周期。

解析：把局部数组地址放进队列，函数返回后消费者再读取，就是典型悬空指针。DMA 缓冲区也不能在尚未处理完时被下一轮 DMA 覆盖。可采用双缓冲、固定内存池或“空闲队列/就绪队列”明确所有权转换。

4.7 环形缓冲区要解决哪些边界？

答案：要定义读写索引、满和空的判定、溢出策略以及并发读写规则。

解析：常见做法是保留一个空槽：next(write) == read 表示满，write == read 表示空；这样容量为数组长度减一。也可以维护计数，但并发时计数更新需保护。单生产者单消费者与多生产者多消费者的同步难度不同。溢出时是丢新数据、丢旧数据还是报错，必须按协议要求决定。

4.8 初始化顺序如何安排？

答案：先建立时钟和内存等基础环境，再配置引脚/总线/外设，创建同步对象和任务，最后使能会产生事件的中断或启动采集。

解析：若中断先开而队列/任务句柄尚未建立，ISR 可能在系统未准备好时访问空句柄。不同 RTOS 和芯片的启动限制需核对。初始化函数应返回状态；失败时进入安全状态，而非带着一半配置继续运行。

4.9 错误码、日志和断言如何分工？

答案：可预期的运行错误用返回码或状态处理；诊断信息用日志；违反内部不变量的编程错误用断言在开发期尽早暴露。

解析：I²C NACK 是可能发生的外部错误，不适合无条件断言停机；“队列句柄不可能为 NULL”若发生，说明初始化或代码逻辑有缺陷。日志在实时路径要限频、避免阻塞，并保留时间戳和错误上下文。量产设备还需定义断言后如何安全降级或复位。

4.10 如何验证软件“实时性”？

答案：列出各关键事件的截止期，测量最坏或足够保守的响应路径：中断延迟、ISR 执行、排队等待、任务切换、锁等待和业务处理。

解析：平均耗时很低仍可能偶发超时。用 GPIO 翻转配示波器/逻辑分析仪、硬件计数器或追踪工具测量关键路径；同时施加最不利的并发负载。看门狗、日志和动态分配也可能造成额外抖动。

4.11 什么是可测试的软件结构？

答案：把纯逻辑与硬件访问分开，使协议解析、状态转换、校验和滤波能在电脑上以确定输入测试；硬件接口则用真实板卡做集成验证。

解析：例如解析函数接收 const uint8_t *data 和长度，返回解析状态，不在内部直接调用 UART 寄存器。这样可以喂入正常帧、截断帧、错误校验和随机字节流。硬件测试仍要覆盖中断竞争、电源异常和真实时序。

4.12 模块自测：把口头需求变成规则

题目：① 当前风扇开启，温度从 31 ℃降至 29 ℃，该不该关闭？② 传感器读取失败，但温度变量仍是上次的 27 ℃，可以继续据此关风扇吗？③ 串口接到新阈值，应直接修改控制任务内部变量吗？

答案与推理：① 保持开启，关闭阈值是 28 ℃。② 不能把旧值当成有效新样本，应携带有效性与时间信息并进入规定故障路径。③ 优先发送命令，由状态的拥有者验证范围并在明确时机应用；如果必须共享对象，则定义同步与一致性规则。

5. FreeRTOS 高频题：任务如何并发与协作

以下 API 名称和行为以官方 FreeRTOS Kernel 文档为依据。具体调度选项、任务通知数组、静态分配开关和移植端中断限制须看工程的 FreeRTOSConfig.h。参考 FreeRTOS 调度、任务状态及 队列文档。

5.0 先建立模型：一颗 CPU 怎样表现得像同时做多件事

看一次抢占，不要把 tick 当成唯一切换机会

设系统为单核抢占式配置，处理任务优先级为 3、通信任务为 2、日志任务为 1；都不是中断优先级。忽略中断嵌套和额外运行开销，仅观察调度关系：

时刻 发生的事 CPU 接下来做什么
t0 处理任务等队列；通信任务就绪 运行通信任务
t1 DMA 中断到来，投递样本并唤醒处理任务 先执行 ISR
t2 ISR 请求切换并退出 运行优先级 3 的处理任务
t3 处理完成，处理任务再次等空队列 恢复运行通信任务
t4 通信任务也阻塞 日志任务才有机会运行

处理任务在 t1 前没有资格竞争 CPU，因为它在阻塞态。portYIELD_FROM_ISR() 请求切换后，在端口允许调度的时机执行，常见 Cortex-M 端口用 PendSV 完成上下文切换；不必机械地等到下一个 tick。

一个重要反例：高优先级任务无限调用 taskYIELD()，仍可能饿死低优先级任务。让出 CPU 不会把自己从就绪集合里移除，调度器仍然优先选择最高优先级就绪任务。需要等待事件时应进入阻塞态。

区分“醒了”和“运行了”

到达超时时间只说明任务有机会回到就绪态；如果更高优先级任务占着 CPU，它不会立即运行。常规 tick 正常递增时，vTaskDelay(1) 的阻塞时间可能接近 0，也可能接近一个 tick 周期，取决于调用相位；到实际继续执行还可能更久。

因此 vTaskDelay(1) 不是“精确延时 1 ms”，vTaskDelay(0) 也不是阻塞等待。参考 FreeRTOS vTaskDelay 说明。

中断优先级要同时看数值、分组和表示方式

仅在一个具体的 Cortex-M3/M4 示例中，假设实现 4 位优先级、全部用于抢占，CMSIS 的未移位逻辑优先级范围是 0～15，FreeRTOS 可调用内核 API 的门槛配置为逻辑值 5：

中断逻辑值 能否调用适用的 FromISR API 原因
0～4 不能 紧急程度高于内核允许门槛
5～15 可以，仍须遵守各 API 条件 落在受内核保护的范围

若配置采用常见命名，configMAX_SYSCALL_INTERRUPT_PRIORITY = 5 << (8 - 4) = 0x50；传给 NVIC_SetPriority() 的仍是未移位的 5，不能把 0x50 再当未移位值传进去。换内核、位数或分组时必须重新核对，尤其不能把此例直接套到没有 BASEPRI 的端口。依据见 CMSIS NVIC 接口与 FreeRTOS Cortex-M 说明。

先问要传什么，再选机制

真正的需求 常用机制 必须处理的边界
每份样本都要处理 队列 / 有所有权的缓冲池 队列满、处理速度、生命周期
告诉指定任务去查缓冲区 任务通知 多次事件是否合并、缓冲区是否覆写
多任务轮流占用一个设备 互斥量 持锁时间、锁顺序、超时
等网络和存储都准备好 事件组 位表示状态，不代表无限个事件

队列中的一个元素通常只交给一个成功接收者；多个消费者等待同一队列并不等于广播。二值信号量满了以后不能继续累积更多次数，事件位反复置 1 也不会保存次数。需要逐条保留事件时，要选择能表达数量和载荷的机制。

5.1 任务有哪些常见状态？

答案：运行态 Running、就绪态 Ready、阻塞态 Blocked、挂起态 Suspended；删除中的任务还涉及终止和资源回收过程。

解析：就绪表示“可以运行但暂未获得 CPU”；阻塞表示等待时间或事件，不占用 CPU。vTaskDelay() 后任务进入阻塞而非挂起；vTaskSuspend() 才是显式挂起。单核系统同一时刻通常只有一个任务运行，但中断可打断它。

5.2 FreeRTOS 是怎么决定下一个任务的？

答案：在常见单核、抢占式配置下，调度器选择最高优先级的就绪任务；更高优先级任务就绪时可抢占当前任务。同优先级任务是否按时间片轮转取决于配置。

解析：“优先级高”不代表一直运行：如果它在等队列、通知或延时，就不处于就绪态。也不能笼统说“每个 tick 都切换任务”，因为配置、任务状态和主动让出都会影响切换。任务优先级数字的方向与 Cortex-M 中断优先级相反：FreeRTOS 中通常数字越大越高。

5.3 vTaskDelay() 和 vTaskDelayUntil() 有什么区别？

答案：vTaskDelay(n)（n > 0）按调用时的 tick 计数安排相对唤醒时刻；实际阻塞时长取决于调用相位，不能理解成至少经过 n 个完整 tick 周期；vTaskDelayUntil() 以参考唤醒时间安排固定节拍，更适合周期任务。

解析：任务执行时间若每轮都不同，vTaskDelay() 会把执行时间叠加到周期；固定节拍 API 能减少这种累计漂移。不过超期任务无法靠延时“补回”已经错过的截止期。pdMS_TO_TICKS() 存在 tick 粒度和整数舍入，不能保证精确到 1 ms。

/* 任务函数片段：period 的单位是 tick；需确认转换结果非 0。 */
TickType_t last = xTaskGetTickCount();
const TickType_t period = pdMS_TO_TICKS(10);
configASSERT(period > 0);
for (;;) {
    sample_and_process();       /* 最坏执行时间应小于可用周期预算 */
    vTaskDelayUntil(&last, period);
}

5.4 xTaskCreate() 创建了什么？栈大小单位是什么？

答案：创建任务通常需要任务控制块和任务栈。xTaskCreate() 的栈深度参数以 StackType_t 元素数计，不应直接当成字节数。

解析：在 32 位端口，100 个栈元素通常对应约 400 字节，但仍须看端口定义、对齐和额外开销。任务栈用于该任务的调用链、局部对象及上下文；高水位可以帮助估计余量，但测试必须覆盖最深路径。静态创建则由应用提供控制块和栈存储。参考 FreeRTOS 静态与动态分配。

5.5 vTaskDelay() 与忙等有什么差别？

答案：任务延时会让任务阻塞，其他任务可运行；忙等持续占用 CPU 执行循环。需要等待某事件时，优先采用队列、通知、信号量等事件驱动机制。

解析：while (!flag) {} 即使变量是 volatile，也仍然消耗 CPU。特别是高优先级任务忙等低优先级任务产生的条件，可能使后者根本得不到运行机会。

5.6 队列和任务通知怎么选？

答案：要传递多个独立数据项、支持多个发送方/接收方时，队列更自然；只唤醒指定任务或传递轻量状态/计数时，任务通知通常更轻。

解析：队列默认按创建时的项目大小复制数据；若发送指针，只复制指针值，必须约定缓冲区生命周期。任务通知属于接收任务本身，不能直接代替通用的多接收方消息队列。中断中使用对应 ...FromISR() 接口。参考 FreeRTOS 任务通知。

5.7 二值信号量、计数信号量和互斥量区别是什么？

答案：二值信号量常用于“发生过一次事件”；计数信号量可累计有限数量的事件或资源；互斥量表示共享资源的所有权，带优先级继承机制。

解析：ISR 可给信号量通知任务；ISR 不能像任务那样持有并归还互斥量。保护 I²C 总线由多个任务轮流使用时考虑互斥量；通知采集任务“DMA 完成”考虑任务通知或信号量。互斥量的优先级继承只缓解某些优先级反转，不消除死锁。

5.8 什么是优先级反转？

答案：低优先级任务持有高优先级任务所需的锁，高优先级任务等待；此时中优先级任务不断运行，使低优先级持锁者迟迟不能释放锁，造成高优先级任务被间接拖延。

解析：互斥量的优先级继承会临时提高持锁者优先级，使它尽快完成并释放资源。解决设计问题还要缩短持锁时间、减少共享资源和明确锁顺序。易错点：把二值信号量当互斥量使用，通常得不到互斥量的所有权与继承语义。

5.9 事件组和任务通知位图有什么不同？

答案：事件组适合多个任务等一个或多个条件位，也能选择等待所有位或任一位；任务通知位图属于一个接收任务，通常更轻量。

解析：设置事件位不传输大块数据；它表达“条件发生或成立”。若要可靠处理每一份数据，仍需队列或缓冲区。任务通知的位图等待与事件组的“等所有位”并非完全等价，见 FreeRTOS 任务通知说明。

5.10 为什么 ISR 要用 ...FromISR()，末尾还要请求切换？

答案：中断上下文不能调用可能阻塞的普通任务 API；...FromISR() 是专门为 ISR 设计的接口。若它唤醒更高优先级任务，通常通过移植端提供的 portYIELD_FROM_ISR() 等宏请求退出中断后尽快切换。

解析：xHigherPriorityTaskWoken 初值设为 pdFALSE，交给 API 更新；并核对中断优先级是否落在允许调用内核 API 的范围。实际宏名称和可用范围随移植端变化。

/* 工程片段：worker_task 必须在启用 DMA IRQ 前保存已创建任务的句柄。
 * clear_dma_interrupt_flag 由驱动提供；仅在确认相应完成事件后通知。 */
void DMA_IRQHandler(void)
{
    BaseType_t higher_woken = pdFALSE;
    clear_dma_interrupt_flag();
    vTaskNotifyGiveFromISR(worker_task, &higher_woken);
    portYIELD_FROM_ISR(higher_woken);
}

5.11 临界区、暂停调度器和互斥量能互相替代吗？

答案：不能。临界区用于极短的共享访问保护，但其屏蔽范围取决于端口，不保证屏蔽所有中断；暂停调度器只阻止任务切换，通常不等于屏蔽中断；互斥量用于任务间可能持续较久的资源独占。

解析：持有互斥量的任务可能因其他操作而阻塞，但会延长资源占用，应尽量避免持锁等待不相关事件；临界区内不应调用可能阻塞的 API。共享对象若同时被 ISR 和任务访问，单纯任务互斥量无法阻止 ISR 进入。使用哪一种取决于共享者是谁、持续时间和最坏延迟。

5.12 heap_1 到 heap_5 的常考区别？

答案：heap_1 只分配不释放；heap_2 可释放但不合并相邻空闲块；heap_3 包装标准库 malloc/free；heap_4 可合并相邻空闲块；heap_5 类似 heap_4，还可管理多个不连续内存区域。

解析：选择时看是否动态创建/删除、内存布局和碎片风险。heap_3 的堆大小不由 configTOTAL_HEAP_SIZE 控制。xPortGetFreeHeapSize() 只告诉剩余总量，不直接证明不存在碎片。官方已将 heap_2 视为旧方案，见 FreeRTOS 内存管理。

5.13 软件定时器回调是不是硬件中断？

答案：不是。FreeRTOS 软件定时器回调通常在定时器服务任务上下文执行，不是 ISR。

解析：它受定时器服务任务优先级、命令队列和其他回调执行时间影响，不能把它当精确硬件定时器 ISR。回调应短，不要长时间阻塞，否则同一服务任务中的其他定时器事件也会被拖延。精密采样或 PWM 边沿仍应依赖硬件定时器。

5.14 空闲任务能删吗？任务删除后内存立即全回收吗？

答案：空闲任务是内核运行的一部分，不能随意删除。动态创建任务被删除后的资源回收可能由空闲任务执行，因此空闲任务需要运行机会。

解析：高优先级任务无限忙循环会使空闲任务饥饿。观察到“任务删了但堆未立刻回升”时，先检查空闲任务是否获得 CPU，以及端口/配置和堆实现。任务自己申请的其他资源通常还需要应用自行归还。

5.15 Tickless idle 是否意味着任务延时变准？

答案：不意味着。Tickless idle 是在可空闲一段时间时抑制周期 tick 以降低功耗；时间精度受低功耗计时源、补偿和唤醒延迟影响。

解析：它适合低功耗场景。若需求是微秒级精确动作，优先用硬件定时器或专用外设，而不是把 FreeRTOS tick 调得很快。进入低功耗前还要确认 DMA、外设时钟和唤醒源。

5.16 任务无响应时按什么顺序排查？

答案：先确认任务状态和优先级，再查它等待的对象、超时时间和生产者；之后看栈高水位、断言、堆、ISR 优先级和中断是否触发。

解析：“任务没运行”可能是它正正常阻塞，也可能是高优先级任务忙等、锁未释放、通知送错任务、队列满/空或栈被破坏。排查要用任务状态、时间戳和事件计数证据，而不是随意提高优先级。优先级升高可能掩盖真正的同步错误。

5.17 模块自测：在纸上推演调度

题目：① 优先级 4 的任务忙等优先级 2 的任务设置标志，会怎样？② tick 为 100 Hz，pdMS_TO_TICKS(1) 一定大于零吗？③ 上述四位、门槛 5 的例子中，逻辑优先级 3 的 ISR 能否调用 xQueueSendFromISR()？④ 队列里放结构体指针是否已经复制了结构体？

答案与推理：① 若低优先级任务无法从其他执行机会产生标志，会一直等不到；改成让高优先级任务阻塞等待事件。② 不一定，常见整数转换得到 0，需检查配置与转换定义。③ 不能，它比门槛更紧急，不受内核对应临界区保护。④ 没有，只复制了指针值，必须另外保证对象有效与独占规则。

6. 贯穿案例：每 1 ms 采样，每 10 ms 处理一次

6.1 先写需求和假设，再画任务图

这是一个教学采集控制器，使用单核 MCU，ADC 单通道由硬件定时器每 1 ms 触发，DMA 每收满 10 个样本交给处理任务。处理任务做换算、有效性检查和风扇控制；串口每 10 ms 上报一帧 20 字节状态。

约定：ADC 数据用 16 位无符号数存储；温度换算和有效范围由实际传感器决定；本文不假造传感器标定公式。控制从完整数据块到输出的截止期暂定为 10 ms。若真正需求是“输入变化后 1 ms 内响应”，这种攒 10 个样本的设计就不满足要求。

1 kHz 定时器 → ADC → DMA：半区 A / 半区 B
                          ↓ 半区完成 ISR：复制小块，投递队列
                     处理任务（优先级 3）
                          ↓ 有效温度、状态、时间戳
                     通信任务（优先级 2）
                          ↓ UART 发送，完成前保留发送缓冲区
                     健康监控（按自己的期限安排）

这些是任务优先级；任何 ISR 的紧急程度由 NVIC 独立配置。处理任务等队列、通信任务等消息或传输完成，均采用阻塞等待。

6.2 先算三个数量级

DMA 缓冲区：每半区 10 × 2 = 20 字节，两个半区共 40 字节。每 10 ms 完成一个半区；在稳定连续采样、无额外停顿的这个例子里，完成的半区约 10 ms 后就开始被下一轮覆盖。中断服务延迟和复制时间必须落在这个窗口内，缓存维护另按芯片要求处理。

处理预算：假设测得并保守估计，ISR/交接开销不超过 0.1 ms，处理本身不超过 1.2 ms，等待 CPU、锁及处理中被抢占的累计延迟不超过 0.8 ms，三者没有重复计数，则总计 0.1 + 1.2 + 0.8 = 2.1 ms，比 10 ms 截止期有 7.9 ms 余量。这是带假设的预算；必须在目标板最不利负载下确认这些上界，不能用平均值代替。

串口吞吐：假设 UART 为 115200 bit/s、8N1，每字节含 1 起始位、8 数据位、1 停止位。每秒 100 帧、每帧 20 字节，总需求 100 × 20 × 10 = 20000 bit/s，约占带宽 17.36%；一帧在线传输约 1.736 ms。帧头和校验必须已包含在 20 字节内，否则应重新计入。

反向接收若连续满速，而解析任务可能停顿 50 ms，会积压 115200 ÷ 10 × 0.05 = 576 字节。再预留一帧 64 字节，至少要容纳 640 字节；采用保留一空槽的 1024 字节环形缓冲区，可用容量为 1023 字节。这个估算假设停顿开始时没有其他积压，长期平均消费能力仍必须大于输入速率。

6.3 用“按值入队”说明数据生命周期

下面是 FreeRTOS 工程片段。sample_queue 必须先创建为 xQueueCreate(4, sizeof(SampleBlock))，检查创建结果，建立接收任务，再允许 DMA 产生中断。SDK 负责判断完成的是哪个半区、按规定清标志，并调用下面的回调；该 ISR 的优先级必须允许调用内核 API。

#include <stdint.h>
#include <string.h>
#include "FreeRTOS.h"
#include "queue.h"

enum { SAMPLES_PER_BLOCK = 10 };
typedef struct {
    uint16_t raw[SAMPLES_PER_BLOCK];
} SampleBlock;

static QueueHandle_t sample_queue;
/* 仅由这一接收 ISR 更新；供调试器观察。任务读取需另定同步规则。 */
static volatile uint32_t dropped_blocks;

/* completed 指向的半区在整个复制期间必须稳定，缓存状态也需已处理。 */
void on_dma_half_complete(const uint16_t *completed)
{
    SampleBlock msg;
    BaseType_t higher_woken = pdFALSE;
    memcpy(msg.raw, completed, sizeof msg.raw);
    if (xQueueSendFromISR(sample_queue, &msg, &higher_woken) != pdPASS) {
        ++dropped_blocks;       /* 本例丢弃新块，必须由健康逻辑检测处理 */
    }
    portYIELD_FROM_ISR(higher_woken);
}

/* 平台无关处理由应用提供：换算、有效性检查、控制、生成遥测。 */
extern void process_block(const SampleBlock *block);
void sample_task(void *argument)
{
    (void)argument;
    SampleBlock msg;
    for (;;) {
        if (xQueueReceive(sample_queue, &msg, portMAX_DELAY) == pdPASS) {
            process_block(&msg);
        }
    }
}

队列项目大小是 sizeof(SampleBlock)，因此成功发送时复制的是整个块，ISR 中的 msg 在返回后失效也不影响队列副本。接收任务又得到自己的副本；process_block 若要异步保留数据，仍需复制或另外交接，不能无限期保存 &msg。

这里只复制 20 字节，设计上可以评估 ISR 开销。大数据块更适合固定缓冲池和指针交接，但要增加“空闲 → DMA 占用 → 待处理 → 空闲”的所有权状态。队列容量 4 只能吸收有限抖动，不能修复长期处理不过来的问题。真实控制器还应检测样本超时、丢块和数据连续性，而非只累计一个计数器。

6.4 把风扇逻辑写成可在电脑上验证的 C 程序

以下为完整 C11 教学程序，可保存为 control_demo.c。温度单位是毫摄氏度，30000 即 30 ℃。假设本例故障时输出关闭，恢复需要有效数据与确认动作；这是为示例选择的行为，不能直接替代真实产品的安全策略。

#include <assert.h>
#include <stdbool.h>
#include <stdint.h>
#include <stdio.h>

typedef enum { FAN_OFF, FAN_ON, FAN_FAULT } FanState;

static FanState control_step(FanState previous, bool valid,
                             int32_t milli_celsius, bool acknowledge)
{
    if (!valid) {
        return FAN_FAULT;
    }
    if (previous == FAN_FAULT) {
        if (!acknowledge) {
            return FAN_FAULT;
        }
        previous = FAN_OFF;
    }
    if (previous == FAN_OFF && milli_celsius >= 30000) {
        return FAN_ON;
    }
    if (previous == FAN_ON && milli_celsius <= 28000) {
        return FAN_OFF;
    }
    return previous;
}

int main(void)
{
    FanState state = FAN_OFF;
    state = control_step(state, true, 30000, false);
    assert(state == FAN_ON);             /* 上阈值边界 */
    state = control_step(state, true, 29000, false);
    assert(state == FAN_ON);             /* 滞回区域保留记忆 */
    state = control_step(state, true, 28000, false);
    assert(state == FAN_OFF);            /* 下阈值边界 */
    state = control_step(state, false, 27000, false);
    assert(state == FAN_FAULT);          /* 无效值不能当低温使用 */
    state = control_step(state, true, 29000, false);
    assert(state == FAN_FAULT);          /* 好转不等于自动恢复 */
    state = control_step(state, true, 31000, true);
    assert(state == FAN_ON);             /* 确认后重新判断阈值 */
    assert(control_step(FAN_OFF, true, 29000, false) == FAN_OFF);
    assert(control_step(FAN_ON, false, 31000, true) == FAN_FAULT);
    puts("control tests passed");
    return 0;
}

例如用 GCC：gcc -std=c11 -Wall -Wextra -Werror control_demo.c -o control_demo，运行成功会输出 control tests passed；验证时不要启用 NDEBUG，否则 assert 会被移除。调用方传入合法枚举值，换算层保证有效温度的范围。

业务函数没有读取 GPIO、调用队列或进行延时；应用拿到返回状态后调用驱动设置输出，例如在本例中只有 FAN_ON 输出开启。这个划分让你能单独验证“30 ℃和28 ℃边界正确”“故障不会被旧数值掩盖”，然后再用板卡验证真实引脚和时序。

7. 综合场景题：把知识连起来

先遮住答案，在纸上写出“现象 → 可能机制 → 验证证据 → 修复办法”，再对照解析。

场景 1：串口 115200 bit/s 连续收包，偶尔丢字节，怎么办？

答案：先测丢失发生在硬件接收、DMA/中断缓冲、任务队列还是协议解析层。检查 UART 溢出标志、中断最长关断时间、DMA 缓冲覆盖、队列满次数、解析任务最坏执行时间。

解析：仅按 10 位一帧估算，115200 bit/s 下约每 86.8 μs 到来 1 字节。若 ISR 偶尔被长时间屏蔽，单字节接收中断可能来不及搬走数据。可采用 DMA + 环形/双缓冲、缩短临界区、提高解析吞吐，并记录溢出计数。不要直接把任务优先级调高就当修复；硬件层丢字节时，任务再快也取不回来。

场景 2：高优先级任务在等 I²C 数据，但系统卡住，怎么解释？

答案：先查它是在阻塞等待，还是忙等；查持有 I²C 互斥量的任务是否获得运行机会，是否在持锁期间等待另一个也依赖 I²C 的事件。

解析：若是优先级反转，使用互斥量并缩短持锁时间；若是循环等待，则统一锁顺序、消除锁内阻塞依赖。再查 I²C 总线本身是否被外设拉低，以及超时/恢复路径是否存在。定位时应同时记录任务状态和总线波形。

场景 3：DMA 完成中断触发了，任务读到旧数据，为什么？

答案：可能读错缓冲区、DMA 尚未真正完成有效载荷、CPU 数据缓存未失效、缓冲区被下一轮传输覆盖，或任务与 ISR 的交接缺乏明确同步。

解析：先确认 DMA 状态位与长度，再核对缓冲区地址、对齐和缓存属性；必要时按芯片手册做缓存维护。设计双缓冲或所有权交接，让 DMA 不写任务正在读的区域。volatile 不能代替缓存一致性处理。

场景 4：任务栈偶发溢出，平时高水位却看起来足够，怎么查？

答案：高水位只反映被检测期间栈的使用痕迹；偶发路径、递归、大局部数组、格式化打印和中断嵌套可能未被覆盖。先开启栈溢出检查与断言，再在压力和错误路径下测量。

解析：检查栈大小单位是否误当字节、任务栈与中断栈是否分离、局部数组是否能改为静态缓冲或固定池。别只靠增大栈掩盖无限递归或越界写导致的破坏。

场景 5：按键每按一次，却触发很多次，如何设计？

答案：机械触点会抖动；ISR 可只记录边沿和时间，后续用定时采样或状态机确认稳定按下与释放，再产生一次业务事件。

解析：延时 20 ms 只是常见经验值，需根据器件和需求确定。若在 ISR 内忙等消抖，会拖慢其他中断。状态机还可明确长按、连按和重复触发规则。

场景 6：面试官让你设计一个“采样、控制、通信、升级”的系统，怎么答？

答案：先列每部分频率、截止期和数据量；用硬件定时器触发采样，DMA/ISR 完成数据搬运，控制任务按固定节拍计算，通信任务处理收发，升级服务进入专门状态并保证写 Flash 的安全条件。

解析：模块边界可划为 ADC/通信驱动、采样与控制服务、协议解析、升级管理、业务状态机。任务间通过队列/通知传事件，缓冲区明确定义所有权；共享总线用互斥量；故障管理统一记录超时、复位原因与看门狗健康状态。最后说明将用示波器或追踪工具验证控制路径的最坏响应，而不是只给一张任务列表。
