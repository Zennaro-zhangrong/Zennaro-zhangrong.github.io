上电到复位到复位函数

一句话总结：复位释放时，Cortex-M 内核只从地址 0x00000000 和 0x00000004 取出两个数，分别装进 MSP（栈指针） 和 PC（程序计数器）。此后执行的第一段代码不是 main，而是启动文件里的 Reset_Handler；它把 C 语言运行所需的环境搭好，最后才调用 main。

0. 先分清两种“寄存器”

聊启动流程之前，必须先区分单片机里两个都叫“寄存器”的东西，否则很容易把 RCC->CR 和 R0 混为一谈。

0.1 内核寄存器（Core Registers）

  • 位于 Cortex-M 内核内部，是 CPU 的“手边抽屉”。
  • 有名字：R0~R15、xPSR、PRIMASK、CONTROL 等。
  • 没有地址，不能用指针访问；由指令直接操作，例如 MOV R0, #1、ADD R0, R1、BL main。
  • 数量很少（通用寄存器只有 16 个），速度最快。
  • 作用：存放正在计算的数据、地址、函数返回地址、栈指针、当前指令地址、状态标志。

0.2 外设寄存器（Peripheral Registers）

  • 位于内核外部，是每个外设（GPIO、USART、SPI、RCC、定时器……）的“控制面板”。
  • 每个寄存器都被分配了一个固定地址，通常落在内存映射的 0x40000000 附近。
  • CPU 用普通的 LDR/STR 指令读写它们；C 语言里就是一个 volatile 指针。
  • 作用：配置外设、启动转换、读状态、发数据。写某一位，硬件就执行对应动作。
/* CMSIS 把地址包装成结构体指针 */
#define RCC_BASE   0x40023800UL
#define RCC        ((RCC_TypeDef *) RCC_BASE)

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;   /* 本质：*(volatile uint32_t *)0x40023830 |= 1 */

内核寄存器决定程序怎么走，外设寄存器决定硬件怎么动。 本文前半部分（复位 → main）几乎只涉及内核寄存器；进入 main 之后，才开始大量操作外设寄存器。

1. 上电：复位电路先把内核按住

  1. 当电压从 0 向门限电压上升时，单片机的电源复位电路1一直把内核按在复位状态，CPU 不取指、不执行任何指令。
  2. 电压达到 POR/PDR 门限并稳定一段时间后，复位释放。有的芯片还有 BOR（欠压复位），电压跌到阈值以下会再次把芯片按回复位，防止低压下跑飞。
  3. 复位不是“把整颗芯片清零”。它只把内核和大部分外设置到一个确定的初始状态；SRAM 不会被硬件清零，里面的值可能是随机的，也可能保留上次运行的内容（热复位）。
  4. 复位释放的那一刻，内核才真正开始“苏醒”，并按下一节的固定动作取向量。

2. 复位释放：硬件只做两件事

Cortex-M 内核对复位有一条规定死的动作，不需要任何代码参与：

MSP ← *(uint32_t *)0x00000000     // 第 1 个字：栈顶地址
PC  ← *(uint32_t *)0x00000004     // 第 2 个字：复位向量
  1. 先装 MSP：MSP 是主栈指针2，指向栈顶。函数调用、局部变量、中断压栈都要用栈，所以内核必须在执行第一条指令之前就知道栈在哪里。
  2. 再装 PC：PC 是程序计数器3，装的是下一条要执行的指令地址。复位向量的值不是 main，而是启动文件里的 Reset_Handler。
  3. 这两个值由芯片厂商和链接脚本共同决定，固化在 Flash 起始处。以 STM32F407（128KB SRAM）为例：
地址 典型值（示例） 含义
0x00000000 0x20020000 MSP 初值 = SRAM 顶端
0x00000004 0x08000589 Reset_Handler 地址 0x08000588 + Thumb 位

注意第二个值的最低位是 1。Cortex-M 只支持 Thumb/Thumb-2 指令集，向量最低位就是 Thumb 位4；内核真正跳转时会把它清掉，实际执行地址是 0x08000588。如果这一位是 0，内核会尝试进入 ARM 状态，而 Cortex-M 不支持 ARM 状态，结果就是 UsageFault（INVSTATE）甚至锁死。

复位后的内核状态

项目 复位后的状态
运行模式 Thread 模式
特权级 特权级（Privileged）
使用的栈 MSP
R0~R12 未定义（不要假设为 0）
R13（SP） 向量表第 0 个字
R14（LR） 0xFFFFFFFF
R15（PC） 向量表第 1 个字（最低位为 1）
xPSR T 位为 1（Thumb 状态）
PRIMASK 0（可配置中断全局开放）
CONTROL 0（特权级、使用 MSP）

复位和普通中断不一样：复位不会把寄存器压栈，也不会保存返回地址。内核只是把 MSP 和 PC 装好，然后直接从 Reset_Handler 开始取指。

“内存还没初始化，内容随机”到底指什么？

这句话只说对了一半：

  • SRAM 确实没有初始化。上电后 SRAM 的内容是未定义的；热复位时还可能保留上一次运行的数据。
  • 向量表所在的内存不是随机的。它位于 Flash，烧录时已经写好。复位时读的 0x00000000 只是启动映射的别名，物理上指向 Flash 的 0x08000000（STM32F4 在 BOOT0=0 时）。

0x00000000 为什么能读到 Flash？

Cortex-M 复位时固定从 0x00000000 取向量，但 STM32 的 Flash 物理地址是 0x08000000。中间靠的是启动映射：BOOT 引脚决定把哪块存储区域“贴”到 0x00000000。

BOOT0 BOOT1 0x00000000 映射到 上电后运行什么
0 x 主 Flash（0x08000000） 用户程序
1 0 系统存储器 厂商 ISP Bootloader
1 1 内置 SRAM 特殊调试/测试用途

所以“烧录成功但程序不跑”的一个经典原因，就是 BOOT0 被拉高，芯片进了厂家 Bootloader，根本没执行你的 Reset_Handler。具体引脚定义以所用型号的数据手册为准。

3. 向量表：硬件查的那张表

复位时读的两个字只是向量表5的开头。整张表就是一个 32 位地址数组，放在 Flash 最前面，每个表项 4 字节：

偏移 表项 说明
0x00 初始 MSP 不是函数地址
0x04 Reset_Handler 复位异常，异常号 1
0x08 NMI_Handler 不可屏蔽中断，异常号 2
0x0C HardFault_Handler 硬件错误，异常号 3
0x10 MemManage_Handler 存储器管理错误，异常号 4
0x14 BusFault_Handler 总线错误，异常号 5
0x18 UsageFault_Handler 用法错误，异常号 6
0x1C~0x28 保留 4 项
0x2C SVC_Handler 系统服务调用，异常号 11
0x30 DebugMon_Handler 调试监控，异常号 12
0x34 保留 1 项
0x38 PendSV_Handler 可挂起系统服务，异常号 14
0x3C SysTick_Handler 系统滴答定时器，异常号 15
0x40 起 IRQ0、IRQ1…… 外部中断，异常号 16、17……

几个关键点：

  1. 前两项是数据，不是函数。第 0 项是栈顶地址，第 1 项才是复位处理函数地址。
  2. 表项的值都带 Thumb 位（最低位为 1）。
  3. 异常号 = 表项下标。IPSR 里记录的就是这个编号：复位是 1，SysTick 是 15，外部中断 IRQn 是 16 + n。
  4. 表的位置可以重定位，由 SCB->VTOR 决定6。复位时 VTOR 为 0；SystemInit() 通常会把它设成 0x08000000。如果你写 Bootloader 跳转到 APP，必须手动把 VTOR 改成 APP 的向量表地址，否则中断会跳回 Bootloader 的表。

启动文件里对应的汇编大致如下：

  .section  .isr_vector,"a",%progbits
  .type     g_pfnVectors, %object
g_pfnVectors:
  .word  _estack                 /* 0x00: 初始 MSP */
  .word  Reset_Handler           /* 0x04: 复位 */
  .word  NMI_Handler             /* 0x08 */
  .word  HardFault_Handler       /* 0x0C */
  .word  MemManage_Handler       /* 0x10 */
  .word  BusFault_Handler        /* 0x14 */
  .word  UsageFault_Handler      /* 0x18 */
  .word  0                       /* 0x1C: 保留 */
  .word  0
  .word  0
  .word  0
  .word  SVC_Handler             /* 0x2C */
  .word  DebugMon_Handler        /* 0x30 */
  .word  0                       /* 0x34: 保留 */
  .word  PendSV_Handler          /* 0x38 */
  .word  SysTick_Handler         /* 0x3C */

  /* 外部中断 */
  .word  WWDG_IRQHandler         /* IRQ0，异常号 16 */
  .word  PVD_IRQHandler          /* IRQ1，异常号 17 */
  ...

这里的 NMI_Handler、HardFault_Handler 等通常是弱符号7：

  .weak      NMI_Handler
  .thumb_set NMI_Handler, Default_Handler

意思是：如果你在 C 里写了同名函数，链接器就用你的；如果没写，就全部指向 Default_Handler——一个死循环：

Default_Handler:
Infinite_Loop:
  b  Infinite_Loop

所以程序跑飞后停在 Default_Handler，往往说明触发了某个没处理的中断或异常。调试时先看 IPSR 或调用栈，判断是哪一个。

4. Reset_Handler：真正执行的第一条指令

复位向量指向的 Reset_Handler 位于启动文件8（startup_stm32f407xx.s 之类）里，是芯片上电后执行的第一段代码。它由汇编写成，因为此时 C 语言运行环境还不存在：栈虽然有了，但 .data 还没复制、.bss 还没清零、时钟也可能还是默认的低速时钟。

以 GNU 工具链（STM32CubeIDE）的启动文件为例，删掉无关部分后核心流程如下：

  .syntax unified
  .cpu cortex-m4
  .fpu softvfp
  .thumb

  .section  .text.Reset_Handler
  .weak     Reset_Handler
  .type     Reset_Handler, %function

Reset_Handler:
  /* 1. 再设置一次栈顶（硬件复位时其实已经装过 MSP） */
  ldr   sp, =_estack

  /* 2. 把 .data 段的初值从 Flash 复制到 RAM */
  ldr   r0, =_sdata        /* r0 = RAM 中 .data 的起始地址 */
  ldr   r1, =_edata        /* r1 = RAM 中 .data 的结束地址 */
  ldr   r2, =_sidata       /* r2 = Flash 中 .data 初值的起始地址 */
  movs  r3, #0             /* r3 = 偏移量 */
  b     LoopCopyDataInit

CopyDataInit:
  ldr   r4, [r2, r3]       /* 从 Flash 读一个字 */
  str   r4, [r0, r3]       /* 写到 RAM 对应位置 */
  adds  r3, r3, #4         /* 偏移 +4 */
LoopCopyDataInit:
  adds  r4, r0, r3         /* r4 = 当前目标地址 */
  cmp   r4, r1             /* 到末尾了吗？ */
  bcc   CopyDataInit       /* 没到就继续 */

  /* 3. 把 .bss 段清零 */
  ldr   r2, =_sbss
  ldr   r4, =_ebss
  movs  r3, #0
  b     LoopFillZerobss

FillZerobss:
  str   r3, [r2]           /* 写 0 */
  adds  r2, r2, #4
LoopFillZerobss:
  cmp   r2, r4
  bcc   FillZerobss

  /* 4. 时钟、FPU、向量表偏移 */
  bl    SystemInit

  /* 5. 调用 C/C++ 全局对象的构造函数 */
  bl    __libc_init_array

  /* 6. 进入 main */
  bl    main

LoopForever:
  b     LoopForever        /* main 正常不应该返回 */

这段代码里寄存器在干什么？

寄存器 在这段代码里的角色
SP 指向栈顶；ldr sp, =_estack 把它设到 RAM 末尾
R0 .data 在 RAM 中的目标起始地址
R1 .data 在 RAM 中的目标结束地址
R2 .data 在 Flash 中的初值起始地址（复制时）；.bss 起始地址（清零时）
R3 循环偏移量，每次 +4；清零时固定为 0
R4 临时的当前地址 / 搬运的数据
LR 每次 bl 时由硬件写入返回地址；SystemInit 等函数返回时靠它
PC 每取一条指令自动前进；b、bl、bx 会改写它

ldr sp, =_estack 不是一条真正的“加载绝对地址”指令，而是汇编器的伪指令：它会把 _estack 这个链接脚本符号放进附近的文字池，再生成一条 PC 相对的 ldr。所以本质上还是“从 Flash 里读一个常量到 SP”。

为什么要复制 .data、清零 .bss？

C 语言规定：

  • 有初值的全局变量/静态变量，程序开始时必须等于初值；
  • 没写初值的全局变量/静态变量，程序开始时必须等于 0。

但 RAM 掉电就丢，Flash 又不能像 RAM 一样随意写。于是链接器把初值放在 Flash 里，启动代码再搬到 RAM：

段 放什么 存在哪里 启动时做什么
.text 代码 Flash 不处理
.rodata const 常量、字符串 Flash 不处理
.data 有初值的全局/静态变量 初值在 Flash，运行时在 RAM 从 Flash 复制到 RAM
.bss 无初值或初值为 0 的全局/静态变量 RAM 全部写 0
栈 局部变量、函数调用现场 RAM 设置 SP，不预填
堆 malloc 申请的内存 RAM 由 _sbrk 管理，不预填

9

这也解释了一个常见现象：复位后普通全局变量是确定的，局部变量和 malloc 出来的内存却是不确定的。

不同工具链的启动文件差异

工具链 启动文件 谁负责 .data/.bss 谁调用 main
GCC / STM32CubeIDE startup_stm32f4xxxx.s Reset_Handler 里的汇编 Reset_Handler 中的 bl main
Keil MDK（ARMCC/ARMCLANG） startup_stm32f4xxxx.s C 库的 __main（scatter loading） __main → main
IAR startup_stm32f4xxxx.s __iar_program_start / cstartup __iar_program_start → main

所以你在 Keil 里单步时，会看到 Reset_Handler → SystemInit → __main → main；在 CubeIDE 里则是 Reset_Handler → SystemInit → __libc_init_array → main。入口永远是 Reset_Handler，不是 main。

5. 链接脚本：_estack、_sdata 这些符号从哪来？

启动代码里的 _estack、_sdata、_edata、_sidata、_sbss、_ebss 都不是 C 变量，而是链接脚本10里定义的地址符号。链接器在生成 ELF 时把它们的值算好，启动代码直接把它们当地址常量用。

一个精简过的 STM32F407 链接脚本如下（只保留关键部分）：

/* 1. 存储器布局 */
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
  RAM   (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
}

/* 2. 栈顶 = RAM 末尾 */
_estack = ORIGIN(RAM) + LENGTH(RAM);      /* 0x20020000 */

SECTIONS
{
  /* 3. 向量表必须放在 Flash 最前面 */
  .isr_vector :
  {
    KEEP(*(.isr_vector))
  } >FLASH

  .text   : { *(.text*)   } >FLASH
  .rodata : { *(.rodata*) } >FLASH

  /* 4. .data：运行地址在 RAM，加载地址在 Flash */
  .data :
  {
    _sdata = .;            /* RAM 中的起始地址 */
    *(.data*)
    _edata = .;            /* RAM 中的结束地址 */
  } >RAM AT> FLASH
  _sidata = LOADADDR(.data);  /* Flash 中的初值地址 */

  /* 5. .bss：只占 RAM，不占 Flash */
  .bss :
  {
    _sbss = .;
    *(.bss*) *(COMMON)
    _ebss = .;
  } >RAM
}

关键概念是 VMA（运行地址）和 LMA（加载地址）：

  • .data 的 VMA 在 RAM：程序运行时变量必须能读写。
  • .data 的 LMA 在 Flash：烧录时初值跟着固件一起待在 Flash 里。
  • 启动代码把 [_sidata, _sidata + 长度) 复制到 [_sdata, _edata)。

用一张图表示：

Flash (0x08000000)                          RAM (0x20000000)
┌──────────────┐                            ┌──────────────┐
│ 向量表        │ 0x08000000                 │ .data         │ ← _sdata
│ .text        │                            │  (初值副本)    │
│ .rodata      │                            ├──────────────┤ ← _edata
│ .data 初值    │ ← _sidata                 │ .bss          │ ← _sbss
└──────────────┘                            │  (全 0)       │
                                            ├──────────────┤ ← _ebss
                                            │ 堆 →          │
                                            │              │
                                            │          ← 栈 │ ← _estack
                                            └──────────────┘

两个容易忽略的细节：

  1. KEEP(*(.isr_vector)) 是为了防止链接器开启 --gc-sections 后把“看起来没人引用”的向量表删掉。
  2. 链接脚本里的 ENTRY(Reset_Handler) 只是告诉链接器 ELF 的入口符号，方便调试器/加载器；真正上电时，硬件并不看 ELF 入口，而是看 0x00000004 处的向量。所以即使 ELF 入口写的是 main，芯片照样从 Reset_Handler 开始跑。

编译完成后，可以在 .map 文件里搜索这些符号，确认它们的具体地址。比如：

_estack   0x20020000
_sidata   0x08004a10
_sdata    0x20000000
_edata    0x20000000   /* 如果没有 .data，三者可能相等 */
_sbss     0x20000000
_ebss     0x20000084

.data 和 .bss 的地址取决于工程里全局变量的数量和大小，每次编译都可能变化。

6. SystemInit：把芯片从“能跑”调到“跑得快”

SystemInit() 是复位后执行的第一个 C 函数（在 GCC 启动流程里，它前面只有搬数据和清 .bss 的汇编）。它主要做三件事：

  1. 打开 FPU（如果芯片有）：给 SCB->CPACR 的 CP10、CP11 位写 1，否则浮点指令会触发 UsageFault。
  2. 设置向量表偏移：把 SCB->VTOR 指向 0x08000000，这样后续中断才能查到正确的向量表。
  3. 配置基础时钟：STM32F4 复位后默认跑内部 HSI 16MHz；SystemInit 通常会把时钟切到外部 HSE + PLL，常见的 STM32F407 配置是 168MHz。

示意代码（不同固件库版本细节略有差异，以工程里的 system_stm32f4xx.c 为准）：

void SystemInit(void)
{
  /* 1. FPU：CP10/CP11 全访问 */
  SCB->CPACR |= (0xFUL << 20);

  /* 2. 向量表放到 Flash 起始处 */
  SCB->VTOR = 0x08000000UL;

  /* 3. 配置 HSE + PLL，把 SYSCLK 切到 168MHz */
  SetSysClock();
}

以 STM32F407 的常见配置为例：

时钟 值 说明
HSE 8MHz 外部晶振
PLL_M / PLL_N / PLL_P 8 / 336 / 2 VCO 输入 1MHz，VCO 336MHz，SYSCLK 168MHz
PLL_Q 7 48MHz（USB/SDIO/RNG）
SYSCLK / HCLK 168MHz AHB 不分频
PCLK1（APB1） 42MHz 4 分频
PCLK2（APB2） 84MHz 2 分频
Flash 等待周期 5 WS 168MHz、2.7~3.6V 供电

注意顺序：先调高 Flash 等待周期，再切高频；降频时反过来。否则高频下 Flash 来不及取指，程序会跑飞。HAL_RCC_ClockConfig() 内部会处理这个顺序。

SystemInit 和 SystemClock_Config 是什么关系？

CubeMX 生成的 main.c 里还有一个 SystemClock_Config()，它也会配置 RCC。两者并不冲突：

  • SystemInit()：启动早期执行，保证 C 环境能用、向量表就位、时钟至少能跑；不同固件库版本里它配置的时钟深度不同。
  • SystemClock_Config()：main() 里显式调用，对 HSE、PLL、AHB/APB 分频、Flash 等待周期做一次完整配置，最终以它为准。
  • HAL_RCC_ClockConfig() 在改完时钟后会更新全局变量 SystemCoreClock，并重新调用 HAL_InitTick()，保证 SysTick 仍然是 1ms。

所以如果你在 main() 里改了时钟树，一定要用 CubeMX 重新生成或手动同步 SystemClock_Config()，不要只改一处。

另外要注意工具链差异：在 Keil 的启动流程里，SystemInit 在 __main 之前执行，此时 .data 还没复制；所以 SystemInit 里不要依赖带初值的全局变量。GCC 的启动文件则先复制 .data，再调用 SystemInit。

7. __libc_init_array：C++ 全局对象的构造函数

__libc_init_array() 是 C 库提供的函数，负责：

  • 调用 .init 段里的初始化代码；
  • 遍历 .init_array 段，调用其中保存的函数指针；
  • 这些函数指针包括 C++ 全局对象的构造函数、__attribute__((constructor)) 标记的函数等。

如果你只用 C 语言，这个函数通常什么也不做；但它仍然会被调用，以保证 C++ 工程和带构造函数的库能正常工作。

注意：这些构造函数在 main() 之前执行，但此时外设还没有初始化（HAL_Init()、SystemClock_Config() 都还没跑）。所以不要在全局对象的构造函数里操作外设，除非你确认时钟和 GPIO 已经配好。

8. main：一个被启动代码调用的普通函数

当 Reset_Handler 执行到 bl main 时：

  1. BL 指令把下一条指令的地址写进 LR（最低位为 1），作为 main 的返回地址11。
  2. PC 被改成 main 的地址。
  3. CPU 开始执行 main 的第一条指令。

此时寄存器大致是：

寄存器 值
PC main 的入口地址
SP _estack（main 的序言还没压栈）
LR Reset_Handler 中 bl main 的下一条指令地址（最低位为 1）
R0~R3 未定义；main 没有参数，不会使用
xPSR T 位为 1

main 的序言通常会长这样：

main:
  push  {r7, lr}       /* 保存帧指针和返回地址到栈 */
  sub   sp, sp, #8     /* 给局部变量留空间 */
  ...

push 会让 SP 向下移动；函数返回时 pop {r7, pc} 把返回地址直接弹进 PC，完成返回。这就是为什么 SP 必须一开始就指向一块合法的 RAM。

一个 CubeMX 工程的 main() 通常按这个顺序执行：

int main(void)
{
  HAL_Init();              /* SysTick 1ms、NVIC 优先级分组、Flash 预取 */
  SystemClock_Config();    /* HSE + PLL → 168MHz */
  MX_GPIO_Init();          /* 使能 GPIO 时钟、配置引脚 */
  MX_USART1_UART_Init();   /* 配置串口 */
  /* ... 其他外设初始化 ... */

  while (1)
  {
    /* 主循环 */
  }
}

其中：

  • HAL_Init() 会把 SysTick 配成 1ms 中断，并设置 NVIC 优先级分组；此时用的还是当前时钟（可能是 16MHz，也可能 SystemInit 已经切到了 168MHz）。
  • SystemClock_Config() 改完时钟后，HAL_RCC_ClockConfig() 会重新初始化 SysTick，把它保持为 1ms。
  • 之后的 MX_xxx_Init() 才开始操作外设寄存器，比如 RCC->AHB1ENR 使能 GPIO 时钟、GPIOA->MODER 配置引脚模式。

如果 main() 返回，启动文件里的 LoopForever: b LoopForever 会让 CPU 原地死循环；在 Keil/IAR 里则可能进入 C 库的退出流程。所以 main() 不应该返回，标准的写法是末尾放一个 while (1)。

9. 核心寄存器速查

9.1 通用寄存器和特殊寄存器

寄存器 别名/编号 作用 复位时/启动时的表现
R0~R3 参数/返回值 函数调用的前 4 个参数；返回值放在 R0（64 位返回值用 R0:R1） 未定义
R4~R11 被调用者保存 局部变量；函数如果用到，必须先 push 保存、返回前恢复 未定义
R12 IP 临时寄存器，调用间隙使用 未定义
R13 SP 栈指针，指向栈顶；具体是 MSP 还是 PSP 由 CONTROL.SPSEL 决定 MSP = 向量表[0]
R14 LR 链接寄存器：BL 写入返回地址；中断时写入 EXC_RETURN 0xFFFFFFFF
R15 PC 程序计数器：下一条要执行的指令地址 向量表[1] & ~1
xPSR 程序状态寄存器 条件标志（N/Z/C/V/Q）+ 当前异常号（IPSR）+ Thumb 位（EPSR.T） T=1（0x01000000）
PRIMASK 中断屏蔽 置 1 后屏蔽所有可配置中断（NMI/HardFault 除外） 0
BASEPRI 优先级屏蔽 屏蔽优先级不低于该值的中断 0
FAULTMASK 故障屏蔽 置 1 后连 HardFault 也被屏蔽（只剩 NMI） 0
CONTROL 控制寄存器 bit0 nPRIV：0 特权/1 非特权；bit1 SPSEL：0 MSP/1 PSP；bit2 FPCA：浮点上下文活跃 0（特权、MSP）

12 13

几个容易混的点：

  • SP 不是单独的第 17 个寄存器，它就是 R13。Cortex-M 有两个物理栈指针：MSP（主栈）和 PSP（进程栈），同一时刻只有一个作为 SP 使用。复位后 CONTROL.SPSEL=0，用的是 MSP；RTOS 切换任务时常把任务栈设为 PSP。
  • 栈是满递减的：SP 指向最后一个已压入的字；压栈时先减 4 再写，出栈时先读再加 4。初始 SP = 0x20020000，第一次 push 后变成 0x2001FFFC。
  • AAPCS 要求函数调用边界处 SP 保持 8 字节对齐。编译器会在序言里用 push 的数量和 sub sp 调整来满足；手写汇编调用 C 函数时要注意这一点。
  • 读 PC 得到的不是“当前正在执行的指令地址”，而是“当前指令地址 + 4”（M3/M4 的三级流水线）。调试器里显示的 PC 则是下一条要执行的指令，两者不要混。
  • BL 写入 LR 的返回地址最低位是 1，表示返回后仍处于 Thumb 状态；BX LR 会据此保持 Thumb 模式。

9.2 外设寄存器：地址就是接口

外设寄存器不在内核里，而是挂在内存总线上。CMSIS 头文件把它们定义成结构体指针，本质上就是固定地址：

#define RCC_BASE     0x40023800UL
#define GPIOA_BASE   0x40020000UL

#define RCC          ((RCC_TypeDef *) RCC_BASE)
#define GPIOA        ((GPIO_TypeDef *) GPIOA_BASE)

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;   /* 0x40023830 bit0 = 1，开 GPIOA 时钟 */
GPIOA->MODER &= ~(3U << (5 * 2));      /* 清 PA5 的模式位 */
GPIOA->MODER |=  (1U << (5 * 2));      /* PA5 设为通用输出 */
GPIOA->BSRR  =  (1U << 5);             /* PA5 输出高电平 */

常用外设寄存器地址（STM32F4）：

寄存器 地址 作用
RCC->CR 0x40023800 时钟源使能（HSI/HSE/PLL）
RCC->PLLCFGR 0x40023804 PLL 倍频/分频参数
RCC->CFGR 0x40023808 系统时钟源、AHB/APB 分频
RCC->AHB1ENR 0x40023830 GPIOA~GPIOH 等时钟使能
RCC->CSR 0x40023874 复位原因标志、LSI
FLASH->ACR 0x40023C00 Flash 等待周期、预取、Cache
GPIOA->MODER 0x40020000 引脚模式（输入/输出/复用/模拟）
GPIOA->ODR 0x40020014 输出数据
GPIOA->BSRR 0x40020018 原子置位/复位
SCB->VTOR 0xE000ED08 向量表偏移
SCB->CPACR 0xE000ED88 FPU 访问权限
SysTick->CTRL 0xE000E010 SysTick 控制/状态
SysTick->LOAD 0xE000E014 SysTick 重装载值
NVIC->ISER[0] 0xE000E100 使能外部中断 0~31

写外设寄存器时，volatile 不能省：

/* 正确：每次都真正读硬件 */
while ((USART1->SR & USART_SR_RXNE) == 0) { }

/* 错误：编译器可能只读一次，然后死循环 */
uint32_t sr = USART1->SR;
while ((sr & USART_SR_RXNE) == 0) { }

CMSIS 里的外设结构体成员本身已经带了 volatile，所以用 USART1->SR 是安全的；但如果你自己定义指针，记得加 volatile。

10. 中断：硬件自动压栈，LR 变成 EXC_RETURN

启动流程里 LR 只用来保存函数返回地址，但中断发生时它还有第二种身份。

当外部中断或异常被响应时，硬件会自动做这些事：

  1. 把当前 R0~R3、R12、LR、PC、xPSR 压入当前栈（MSP 或 PSP），共 8 个字、32 字节；如果使用了 FPU，还可能额外压入浮点上下文。
  2. 把 LR 设成一个特殊值 EXC_RETURN14，例如：
    • 0xFFFFFFF9：返回 Thread 模式，使用 MSP；
    • 0xFFFFFFFD：返回 Thread 模式，使用 PSP；
    • 0xFFFFFFF1：返回 Handler 模式，使用 MSP。
  3. 把 PC 设为向量表中对应异常/中断的入口地址。
  4. 把 IPSR 设为异常号，例如 SysTick 是 15，外部中断 IRQn 是 16 + n。

中断服务函数返回时，编译器生成的 BX LR 会把 EXC_RETURN 写回 PC；内核识别到这个特殊值后，自动把之前压栈的 8 个寄存器弹回来，恢复现场。这就是为什么中断函数可以用普通 C 函数写，而不需要手写保存/恢复寄存器的汇编。

一个使能外部中断的例子：

/* 使能 EXTI0 中断（IRQ6，异常号 22） */
NVIC_EnableIRQ(EXTI0_IRQn);
NVIC_SetPriority(EXTI0_IRQn, 5);

/* 中断服务函数：名字必须和启动文件里的向量表一致 */
void EXTI0_IRQHandler(void)
{
  /* 处理中断 */
}

12. 动手验证：用调试器把过程看一遍

只看文字容易忘，建议拿一块 STM32F4 开发板，按下面的步骤实际看一遍。

12.1 看向量表

在调试器里暂停程序，打开 Memory 窗口，输入 0x08000000，按 32 位显示：

  • 第 1 个字应该等于 Registers 窗口里的 MSP（例如 0x20020000）；
  • 第 2 个字应该是一个奇数地址（最低位为 1），例如 0x08000589；
  • 把它减 1（清掉 Thumb 位），就是 Reset_Handler 的实际地址，可以在 Disassembly 窗口里跳过去确认。

也可以用命令行：

arm-none-eabi-objdump -s -j .isr_vector build/Debug/你的工程.elf
arm-none-eabi-nm build/Debug/你的工程.elf | grep -E "Reset_Handler|_estack"
arm-none-eabi-readelf -h build/Debug/你的工程.elf   # 看 Entry point

12.2 单步看启动流程

  1. 在 Reset_Handler、SystemInit、main 三处下断点。
  2. 复位芯片，程序会先停在 Reset_Handler。查看：
    • MSP = 0x20020000（或你的 RAM 顶端）；
    • PC = 0x0800xxxx（Reset_Handler 地址）；
    • LR = 0xFFFFFFFF；
    • xPSR = 0x01000000（T 位为 1）。
  3. 单步执行 ldr sp, =_estack，确认 SP 仍然是 0x20020000。
  4. 继续单步，观察 R0~R4 在复制 .data、清零 .bss 时的变化；PC 每次增加 2 或 4，因为 Thumb-2 指令有 16 位和 32 位两种长度。
  5. 执行 bl SystemInit 时按 Step Into，观察 PC 跳到 SystemInit，同时 LR 变成 Reset_Handler 中的返回地址。
  6. 从 SystemInit 返回后，PC 回到 Reset_Handler 的下一条；再执行 bl main，进入 main。
  7. 在 main 入口确认 LR 是 bl main 的下一条地址（最低位为 1），SP 仍然是 _estack。

12.3 看 .data 和 .bss

在 main() 里加两个全局变量：

volatile uint32_t g_data = 0x11223344;  /* .data */
volatile uint32_t g_bss;                 /* .bss */

然后在调试器里：

  • 查看 g_data 的地址，应该在 RAM（0x2000xxxx）；
  • 查看 g_bss 的地址，也应该在 RAM，值应该是 0；
  • 在 Memory 窗口跳到 _sidata，应该能看到 0x11223344 这份初值还留在 Flash 里。

12.4 看时钟和 SysTick

在 SystemClock_Config() 执行前后分别查看：

寄存器/变量 复位刚释放时 SystemClock_Config() 之后
RCC->CFGR 的 SWS 位 00（HSI） 10（PLL）
SystemCoreClock 16 000 000 168 000 000
SysTick->LOAD 未启动（0） 167 999（1ms @ 168MHz）

注意：SystemCoreClock 是一个软件变量，可能要到 SystemClock_Config() 里才被更新。如果 SystemInit() 已经把硬件时钟切到 168MHz，进入 main() 时硬件可能已经是 168MHz，但变量值不一定同步；SystemClock_Config() 前后看起来“没变化”也很正常。判断实际时钟以 RCC->CFGR 的 SWS 位为准：10 表示系统时钟来自 PLL。

12.5 看复位原因

在 main() 开头加一段：

uint32_t csr = RCC->CSR;
if (csr & RCC_CSR_PORRSTF)  { /* 上电复位 */ }
if (csr & RCC_CSR_PINRSTF)  { /* NRST 引脚复位 */ }
if (csr & RCC_CSR_SFTRSTF)  { /* 软件复位 */ }
if (csr & RCC_CSR_IWDGRSTF) { /* 独立看门狗复位 */ }
if (csr & RCC_CSR_WWDGRSTF) { /* 窗口看门狗复位 */ }
if (csr & RCC_CSR_LPWRRSTF) { /* 低功耗复位 */ }
RCC->CSR |= RCC_CSR_RMVF;       /* 清标志，方便下次判断 */

这段代码放在 main() 里越早越好，避免标志被其他代码清掉。上电复位时 PORRSTF 和 PINRSTF 可能同时置位，这是正常的。

13. 常见误区

  1. “main 是程序入口”：不是。硬件入口是向量表第 1 项指向的 Reset_Handler；main 只是启动代码最后调用的一个普通函数。
  2. “复位后 PC 指向 main”：不是。PC 先指向 Reset_Handler，由它完成运行环境准备后再 bl main。
  3. “0x00000000 就是 Flash”：它是启动映射的别名。STM32F4 在 BOOT0=0 时把 0x08000000 的 Flash 映射到 0x00000000；物理 Flash 仍然是 0x08000000。
  4. “MSP 初值是 0”：不是。MSP 初值是栈顶地址，通常是 RAM 末尾，例如 0x20020000。栈从高地址向低地址生长。
  5. “复位会把 RAM 清零”：不会。硬件只复位寄存器和外设状态；.bss 清零是启动代码做的，.data 复制也是启动代码做的。
  6. “复位后时钟就是 168MHz”：STM32F4 复位默认是 HSI 16MHz；要经过 SystemInit() / SystemClock_Config() 才切换到 HSE+PLL。
  7. “复位后中断全是关的”：PRIMASK=0，全局可配置中断是开放的；但 NVIC 里每个中断的使能位复位为 0，SysTick 也没启动。所以实际不会有中断进来，但不是因为 PRIMASK。
  8. “外设寄存器不用 volatile”：编译器不知道硬件会改变寄存器的值，优化后可能只读一次。CMSIS 结构体成员已带 volatile；自己写指针时一定要加。
  9. “Bootloader 跳 APP 直接跳过去就行”：不行。硬件只在复位时自动装 MSP、取复位向量；跳转前要手动设置 MSP、VTOR，并用 |1 保留 Thumb 位。
  10. “调试器复位 = 上电复位”：不一定。调试器的 reset 可能只复位内核，不断电、不清 RAM、不复位所有外设；观察启动流程时以实际复位源为准。

14. 小结

把整篇文章压缩成三句话：

  1. 硬件只做两件事：从 0x00000000 装 MSP，从 0x00000004 装 PC，然后跳到 Reset_Handler。
  2. 启动代码只做三件事：搬 .data、清 .bss、调用 SystemInit 和 C 运行时初始化，最后 bl main。
  3. main 只是一个普通函数：它返回地址在 LR，局部变量在栈上，外设寄存器从这一刻起才真正开始被操作。

记住这个对应关系：

  • PC 决定“走到哪”；
  • SP 决定“函数调用怎么回、现场存在哪”；
  • LR 决定“回到哪”；
  • xPSR 记录“当前状态和异常号”；
  • 外设寄存器决定“硬件怎么动”。

  1. 单片机存在电源复位电路，在【上电】【欠压】时都会触发。常见的复位源还包括 NRST 引脚、看门狗、软件复位等。 ↩︎

  2. MSP（Main Stack Pointer）是主栈指针，本质上是 R13 当前指向的栈。栈用来保存函数调用现场、局部变量、中断压栈的寄存器。Cortex-M 的栈是满递减（Full Descending）的：SP 指向最后一个已压入的字，压栈时先减后写。复位后默认使用 MSP；RTOS 可以把任务栈切换到 PSP。 ↩︎

  3. PC（Program Counter）是 R15，存储下一条要执行的指令地址。Cortex-M 只支持 Thumb/Thumb-2 指令，指令长度可能是 2 字节或 4 字节，所以顺序执行时 PC 每次加 2 或加 4。if、while、goto、函数调用、中断都会改写 PC。代码的执行过程，本质上就是 PC 被不断改写的过程。注意：在代码里直接读 PC 通常得到“当前指令地址 + 4”（流水线偏移）；调试器显示的 PC 是下一条要执行的指令。 ↩︎

  4. Cortex-M 的指令地址最低位为 1 表示 Thumb 状态。向量表中的处理函数地址、BL 写入 LR 的返回地址都带这一位；真正跳转时内核会清掉最低位再取指。如果向量最低位为 0，内核会尝试进入 ARM 状态，而 Cortex-M 不支持 ARM 状态，会触发 UsageFault（INVSTATE）。 ↩︎

  5. 向量表是一个 32 位地址数组，放在启动存储器的起始位置。第 0 项是初始 MSP，第 1 项是复位处理函数，之后依次是 NMI、HardFault 等系统异常和外部中断。Cortex-M 复位时固定从 0x00000000 读取前两项；之后的异常则通过 SCB->VTOR 找到向量表。 ↩︎

  6. VTOR（Vector Table Offset Register）位于 SCB->VTOR（地址 0xE000ED08），保存向量表的基地址。复位值为 0；SystemInit() 通常把它设为 0x08000000。使用 Bootloader 时，APP 必须把 VTOR 改成自己的向量表地址，否则中断会跳到 Bootloader 的向量表。 ↩︎

  7. 弱符号（weak symbol）允许同一个符号有多个定义：链接器优先使用强符号；如果只有弱符号，就用弱符号。STM32 启动文件用 .weak + .thumb_set 把未实现的中断处理函数指向 Default_Handler，这样用户不写某个中断函数也能链接通过。 ↩︎

  8. 启动文件（startup file）通常是 startup_stm32f4xxxx.s，内容包括向量表、Reset_Handler、默认中断处理函数和栈/堆的最小定义。它由汇编写成，是芯片上电后执行的第一段代码。 ↩︎

  9. .data 存放有初值的全局/静态变量，初值在 Flash，运行时复制到 RAM；.bss 存放无初值或初值为 0 的全局/静态变量，启动时在 RAM 中清零。两者都不包括局部变量（局部变量在栈上）和 malloc 的内存（在堆上）。 ↩︎

  10. 链接脚本（linker script，GCC 下通常是 .ld 文件）描述存储器布局、各段放在哪里、符号的地址。_estack、_sdata、_edata、_sidata、_sbss、_ebss 都是链接脚本定义的符号，不是 C 变量。 ↩︎

  11. LR（Link Register）是 R14。BL 指令把返回地址写入 LR；函数返回时执行 BX LR。中断/异常发生时，硬件把 LR 设成 EXC_RETURN 特殊值，异常返回时 BX LR 会触发自动出栈。函数内部如果还要调用其他函数，编译器会先把 LR 压栈保存。 ↩︎

  12. xPSR 由 APSR（条件标志 N/Z/C/V/Q）、IPSR（当前异常号）和 EPSR（Thumb 状态位 T 等）组成。复位后 T=1，表示 Thumb 状态；发生中断时 IPSR 记录异常号，例如 SysTick 是 15，外部中断 IRQn 是 16 + n。 ↩︎

  13. AAPCS（ARM Architecture Procedure Call Standard）规定：R0R3 传递前 4 个参数，返回值放在 R0（64 位返回值用 R0:R1）；R4R11 由被调用者保存；R12 是临时寄存器；函数调用边界处 SP 必须 8 字节对齐。 ↩︎

  14. EXC_RETURN 是中断/异常返回时 LR 中的特殊值，例如 0xFFFFFFF9 表示返回 Thread 模式并使用 MSP，0xFFFFFFFD 表示返回 Thread 模式并使用 PSP。把该值写入 PC（通常通过 BX LR）会触发硬件自动出栈，恢复中断前的寄存器现场。 ↩︎
